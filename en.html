Background

Why ds.hn exists

The name stands for DeepSeek Harness Network — a public doorway for every locally-running dsh (DeepSeek Harness). dsh is a web UI that runs on your own machine. That's great — until you want to continue a session from your phone, check on a long task from outside, or hand the UI to a colleague for a look. Then you need to expose 127.0.0.1 to the internet, and there are two traps:

First, generic tunnels simply don't work. dsh's /api sits behind a browser-trust fence: any request whose Host isn't loopback gets a 403. ngrok, frp and friends forward the public Host verbatim — the page loads, every API call fails.

Second, a bare exposure hands out a remote shell. dsh ships bash and filesystem tools. An ungated public dsh is a terminal on your machine that anyone can use.

dshn solves both at once precisely because it is a plugin: inside dsh it rewrites each forwarded request's Host/Origin back to loopback, so the trust fence passes it as a local request; meanwhile every public visitor must get through the relay's login gate first. Security lives in the gate, not in fighting the fence.

Capabilities

Everything included, out of the box

⚡️

One-minute signup, zero approval

A subdomain prefix plus a password — that's the whole credential. No tokens, no env vars, no review queue. First come, first served: whoever claims a free subdomain sets its password (stored server-side only as a scrypt hash).

🚪

Login gate

Public visitors must present the same password, exchanged for a host-scoped, HMAC-signed cookie before anything is proxied. 8 wrong guesses in 15 minutes locks that visitor's IP out for 10 — attackers can't lock you out.

🔐

End-to-end encryption

Set a separate E2E password (never sent to any server) and API content is sealed with AES-256-GCM — the relay operator and Cloudflare see only ciphertext. Learn more →

🌍

Cloudflare edge

All *.ds.hn traffic rides Cloudflare's global edge: free DDoS protection, WAF, TLS, Anycast acceleration — and the origin IP stays hidden.

🧩

Native to dsh

Configuration lives in dsh's own Settings under "Public forwarding"; a persistent sidebar entry shows live tunnel latency (~18ms measured through Cloudflare). Not a bolt-on script — a first-class plugin.

🔁

Self-healing connection

Both ends heartbeat every 25 seconds and reconnect automatically. Credentials persist in local config, so the tunnel comes back on its own after a dsh restart.

📡

Full protocol replay

HTTP and dsh's event WebSockets are replayed in full over one multiplexed WSS. A realistic page load of 40 bundles completes with zero failures.

🛡

Management stays on-machine

The plugin's management routes return 404 through the tunnel — reconfiguring or reading the password only works on your own machine. Subdomains are ≥4 chars, passwords ≥8, and disconnecting asks twice.

End-to-end encryption

Ciphertext through the middle, plaintext only at the ends

The login gate keeps strangers out; end-to-end encryption goes further — not even the relay operator or Cloudflare can read your session content. You set one extra 🔒 E2E password that is never sent to any server: your browser encrypts with it, your machine decrypts with it, and every hop in between handles only ciphertext.

Key derivation

The E2E password is stretched with PBKDF2-SHA256 (210,000 rounds, random salt) into an AES-256-GCM key. The salt is public; the password and key never leave your devices.

🙈

Zero content on servers

All API content and event streams crossing the relay and Cloudflare are ciphertext — even if the server were breached, captured traffic would be unreadable.

📦

What gets sealed

/api requests and responses plus downstream event messages. The app shell and static assets stay plaintext so the browser can bootstrap.

🎚

Set once, opt-in

Fill the 🔒 field in the setup panel once. Remote visitors see an unlock prompt on first visit and enter the same E2E password. Local 127.0.0.1 access is untouched.

Honest boundary: this defeats a passive or curious relay and after-the-fact data breaches. The page's JS is still served by the relay, so it does not defeat a relay that actively tampers with the page — see Security.

How it works

Four hops, one trick

Four hops sit between a browser and your machine. The relay is a self-hosted dumb pipe — it checks passwords and moves bytes. The real magic is the last hop, where the plugin turns each request back into what dsh considers a local one.

Credentials are the registration

There is no account system. The first plugin to connect with a free subdomain claims it and its password hash is persisted; every later connection and browser login must match it — squatting-proof by construction.

Outbound only, no public IP

The plugin dials out over WSS to the relay. Home broadband, behind NAT, corporate networks — all fine, no router configuration.

The relay just moves bytes

With end-to-end encryption on, the relay and Cloudflare carry only ciphertext; decryption happens exclusively in your browser and on your machine.

Sign up & onboarding

Live in four steps

No signup page anywhere — registration happens inside dsh's own UI.

Install the plugin

Add dshn-agent to your dsh profile:

dsh plugin --profile web add /path/to/dshn/dist/dshn-agent

Start dsh and open it locally

Start as usual, then open the local address in a browser:

dsh --profile web
# open http://127.0.0.1:3080

Pick a name, set a password, hit "Connect"

A setup panel appears on first local open (also under Settings → Public forwarding): choose a subdomain prefix (≥4 chars) and an access password (≥8, with a strength meter), and we recommend filling the 🔒 field with an end-to-end encryption password right away — so the relay sees only ciphertext from day one. Hit "Connect" and the panel shows your public URL.

Reach it from anywhere

Open https://yourname.ds.hn on your phone or any device and log in with the same access password. With E2E on, an unlock prompt follows — enter the E2E password and you're in.

⚠️ Three things you must know
  • The password is the credential and cannot be recovered server-side. Copy it from the panel before disconnecting — the claimed subdomain answers to this password only.
  • Run exactly one plugin instance per subdomain. Two machines with the same credentials knock each other off in a loop.
  • End-to-end encryption applies to remote access only. Opening 127.0.0.1 locally shows no unlock prompt — by design, not by failure.
Security

Boundaries, stated plainly

A publicly reachable dsh is, at heart, a remote shell. dshn puts both the risk and its limits on the table:

✅

The login gate cannot be disabled. Nothing is proxied to your machine before the password is verified and exchanged for a signed cookie.

✅

Brute force is rate-limited. 8 wrong guesses in 15 minutes → a 10-minute lockout, keyed on (subdomain, visitor IP) — an attacker only locks themselves out.

✅

Management routes never leave your machine. Reading the password, reconfiguring, or disconnecting all 404 through the tunnel, even for a logged-in visitor.

✅

E2E defeats the curious relay. With it on, API content is sealed with AES-256-GCM; the relay operator and Cloudflare see ciphertext, and a server breach yields nothing readable.

⚠️

It does not defeat an actively malicious relay. The page itself (its JS) is still served by the relay, so a relay that tampers with the page could in principle bypass E2E. Fixing that takes TLS passthrough or a native client — we don't pretend otherwise.

💡

Heavy throughput can go direct. Cloudflare may reset the tunnel under sustained load; the plugin supports a direct-to-origin mode (with a pinned self-signed cert) that bypasses the edge.

FAQ

Common questions

What does the name ds.hn mean?
DeepSeek Harness Network — a network of locally-running dsh (DeepSeek Harness) instances, each joining the public internet as yourname.ds.hn.
Why not ngrok / frp / Cloudflare Tunnel?
Generic tunnels forward the public Host verbatim, which dsh's /api browser-trust fence rejects with 403 — the page loads, every API call fails. They also ship with no login gate, leaving a remote shell naked on the internet. As a dsh plugin, dshn rewrites Host/Origin internally and enforces login — both problems solved at once.
How are subdomains assigned? Can mine be squatted?
First come, first served: the first plugin to connect with a free subdomain claims it and sets its password (stored only as a scrypt hash). From then on, connecting with that subdomain requires the same password — a squatter without your password cannot displace you.
What if I forget the password?
It cannot be recovered server-side (the server holds only a hash). As long as your plugin is still running locally, you can view and copy the current password from the panel at any time — so copy it somewhere safe before disconnecting. Credentials also persist in your local dsh config.
Where does traffic flow? Any limits?
Browser → Cloudflare edge → self-hosted relay → the plugin on your machine → local dsh. Edge bandwidth is unmetered. Known limits: Cloudflare's free plan caps a single request body at 100MB, and sustained heavy throughput is better served by the direct-to-origin mode.
Does my machine need a public IP or port forwarding?
No. The plugin dials an outbound WSS connection to the relay — home broadband, NAT, and corporate networks all work.
What exactly does end-to-end encryption cover?
/api request/response bodies and downstream event messages (PBKDF2-SHA256 with 210,000 rounds → AES-256-GCM). The app shell and static assets stay plaintext so the browser can bootstrap. The E2E password is never sent to a server; visitors enter it in the browser and decryption happens locally.
