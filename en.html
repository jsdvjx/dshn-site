Background

Why ds.hn exists

The name stands for DeepSeek Harness Network — a public gateway for every locally-running dsh (DeepSeek Harness). dsh is a web UI that runs on your own machine; the moment you need to continue a session from your phone, monitor a long-running task from outside, or share the UI with a colleague, you must expose 127.0.0.1 to the internet — which raises two problems:

First, generic tunnels do not work. dsh's /api sits behind a browser-trust fence: any request whose Host is not a loopback address is rejected with 403. ngrok, frp and similar tunnels forward the public Host verbatim — the page loads, but every API call fails.

Second, direct exposure hands over a remote shell. dsh ships bash and filesystem tools; a public dsh without access control is a remote terminal open to anyone.

dshn addresses both precisely because it is a plugin: inside dsh it rewrites each forwarded request's Host/Origin back to loopback, so the trust fence passes it as a local request, while every public visitor must first clear the relay's login gate. Security rests on the gate, not on working around the fence.

Capabilities

Everything included, out of the box

⚡️

One-minute signup, zero approval

A subdomain prefix and a password form the entire credential. No tokens, no environment variables, no review queue — first come, first served: whoever claims a free subdomain sets its password (stored server-side only as a scrypt hash).

🚪

Login gate

Public visitors must present the same password, exchanged for a host-scoped, HMAC-signed cookie before anything is proxied. Eight wrong attempts within 15 minutes locks that visitor's IP out for 10 — an attacker cannot lock out the subdomain's owner.

🔐

End-to-end encryption

Set a separate E2E password (never sent to any server) and API content is sealed with AES-256-GCM — the relay operator and Cloudflare see only ciphertext. Learn more →

🌍

Cloudflare edge

All *.ds.hn traffic rides Cloudflare's global edge: free DDoS protection, WAF, TLS, and Anycast acceleration, with the origin IP hidden from the public.

🧩

Native to dsh

Configuration lives in dsh's own Settings under "Public forwarding"; a persistent sidebar entry shows live tunnel latency (about 18ms measured through Cloudflare). A deeply integrated first-class plugin, not an external script.

🔁

Self-healing connection

Both ends exchange heartbeats every 25 seconds and reconnect automatically after an interruption. Credentials persist in local configuration, so the tunnel restores itself after a dsh restart.

📡

Full protocol replay

HTTP and dsh's event WebSockets are replayed in full over a single multiplexed WSS carrying all traffic. A realistic page load of 40 bundles completes with zero failures.

🛡

Management stays on-machine

The plugin's management routes return 404 through the tunnel; reconfiguring or reading the password is only possible on your own machine. Subdomains require at least 4 characters, passwords at least 8, and disconnecting requires a two-step confirmation.

End-to-end encryption

Ciphertext through the middle, plaintext only at the ends

The login gate keeps unauthorized visitors out; end-to-end encryption goes further — session content is unreadable to the relay operator and to Cloudflare alike. You set one additional 🔒 E2E password that is never sent to any server: your browser encrypts with it, your machine decrypts with it, and every intermediate hop carries only ciphertext.

Key derivation

The E2E password is stretched with PBKDF2-SHA256 (210,000 rounds, random salt) into an AES-256-GCM key. The salt is public; the password and the key never leave your devices.

🙈

Zero content on servers

All API content and event streams passing through the relay and Cloudflare are ciphertext — even in the event of a server breach, captured traffic remains unreadable.

📦

What is sealed

/api requests and responses plus downstream event messages. The application shell and static assets remain plaintext so the browser can bootstrap.

🎚

Set once, opt-in

Configure the 🔒 field in the setup panel once. Remote visitors see an unlock prompt on first visit and enter the same E2E password. Local 127.0.0.1 access is unaffected.

Capability boundary: end-to-end encryption defeats passive reading by the relay and after-the-fact data breaches. The page's JS is still served by the relay, so it does not defeat a relay that actively tampers with the page — see Security.

Architecture

How it works

Four hops sit between a browser and your machine. The relay is a self-hosted transparent pipe that only verifies passwords and forwards bytes; the key mechanism is the final hop, where the plugin restores each request to what dsh regards as a local one.

Credentials are the registration

There is no account system. The first plugin to connect with a free subdomain completes the claim and its password hash is persisted; every subsequent connection and browser login must match the same password — squatting is ruled out by construction.

Outbound only, no public IP

The plugin initiates an outbound WSS connection to the relay. Home broadband, NAT, and networks without a public IP all work, with no router configuration.

The relay only forwards bytes

With end-to-end encryption enabled, the relay and Cloudflare handle only ciphertext; decryption occurs exclusively in your browser and on your machine.

Sign up & onboarding

Live in four steps

No signup page is involved — registration takes place entirely within dsh's own UI.

Install the plugin

Install @dshn/agent from npm (fully self-contained; tarball and source installation are covered on GitHub):

dsh plugin --profile web add @dshn/agent

Start dsh and open it locally

Start as usual, then open the local address in a browser:

dsh --profile web
# open http://127.0.0.1:3080

Choose a subdomain, set a password, click "Connect"

A setup panel appears automatically on first local open (afterwards under Settings → Public forwarding): enter a subdomain prefix (at least 4 characters) and an access password (at least 8, with a strength meter). We recommend also setting an end-to-end encryption password in the 🔒 field, so the relay handles nothing but ciphertext from the start. Click "Connect" and the panel shows your public URL.

Reach it from anywhere

Open https://yourname.ds.hn on your phone or any device and log in with the same access password. If end-to-end encryption is enabled, an unlock prompt follows — enter the E2E password to proceed.

⚠️ Three things to know
  • The password is the credential and cannot be recovered server-side. Copy it from the panel and store it safely before disconnecting — the claimed subdomain answers to this password only.
  • Run exactly one plugin instance per subdomain. Two devices sharing the same credentials preempt each other's connection, and the tunnel drops repeatedly.
  • End-to-end encryption applies to remote access only. Opening 127.0.0.1 locally shows no unlock prompt — this is by design.
Security

Boundaries, stated plainly

A publicly reachable dsh is, at heart, a remote shell. dshn states both the risks and the limits of its protections:

✅

The login gate cannot be disabled. Nothing is proxied to your machine before the password is verified and exchanged for a signed cookie.

✅

Brute force is rate-limited. Eight wrong attempts within 15 minutes trigger a 10-minute lockout, keyed on (subdomain, visitor IP) — an attacker locks out only their own IP.

✅

Management routes never leave your machine. Reading the password, reconfiguring, and disconnecting all return 404 through the tunnel, even for a logged-in visitor.

✅

E2E defeats passive reading. With it enabled, API content is sealed with AES-256-GCM; the relay operator and Cloudflare see ciphertext, and a server breach yields nothing readable.

⚠️

It does not defeat an actively malicious relay. The page itself (its JS) is still served by the relay, so a relay that tampers with the page could in principle bypass E2E. A complete fix requires TLS passthrough or a native client — we make no claims beyond what is implemented.

💡

Heavy throughput can go direct. Cloudflare may reset the tunnel under sustained load; the plugin supports a direct-to-origin mode (with a pinned self-signed certificate) that bypasses the edge.

FAQ

Common questions

What does the name ds.hn mean?
DeepSeek Harness Network — a network of locally-running dsh (DeepSeek Harness) instances, each joining the public internet as yourname.ds.hn.
Why not ngrok / frp / Cloudflare Tunnel?
Generic tunnels forward the public Host verbatim, which dsh's /api browser-trust fence rejects with 403 — the page loads, but every API call fails. They also provide no login gate by default, leaving a remote shell exposed without protection. As a dsh plugin, dshn rewrites Host/Origin internally and enforces login — both problems solved at once.
How are subdomains assigned? Can mine be squatted?
First come, first served: the first plugin to connect with a free subdomain completes the claim and sets its password (stored only as a scrypt hash). From then on, connecting with that subdomain requires the same password — without it, no one can displace your connection.
What if I forget the password?
It cannot be recovered server-side (the server holds only a hash). As long as your plugin is still running locally, you can view and copy the current password from the panel at any time — store it safely before disconnecting. Credentials also persist in your local dsh configuration.
Where does traffic flow? Any limits?
Browser → Cloudflare edge → self-hosted relay → the plugin on your machine → local dsh. Edge bandwidth is unmetered. Known limits: Cloudflare's free plan caps a single request body at 100MB, and sustained heavy throughput is better served by the direct-to-origin mode.
Does my machine need a public IP or port forwarding?
No. The plugin initiates an outbound WSS connection to the relay — home broadband, NAT, and corporate networks all work.
Can I run this without depending on ds.hn?
Yes. The relay ships as @dshn/relay (npm) and a Docker image, deployable on your own server and domain; dsh agents point at it with DSHN_RELAY_HOST, and every capability works identically. See the self-hosting guide.
What exactly does end-to-end encryption cover?
/api request/response bodies and downstream event messages (PBKDF2-SHA256 with 210,000 rounds → AES-256-GCM). The application shell and static assets remain plaintext so the browser can bootstrap. The E2E password is never sent to a server; visitors enter it in the browser and decryption happens locally.
