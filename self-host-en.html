Self-hosting

Run your own network,
on your own domain

ds.hn is not the only gateway. The relay ships as @dshn/relay (npm) and a Docker image, deployable on your own server and domain; dsh instances install the same @dshn/agent plugin and point at your relay with DSHN_RELAY_HOST — claims, the login gate, and end-to-end encryption all work identically. The full guide lives in SELF-HOSTING.md.

⚠️ Security premise A publicly reachable dsh is a remote shell (dsh ships bash and filesystem tools). The relay's login gate is the only barrier between the internet and that shell — set a strong DSHN_COOKIE_SECRET and strong per-tunnel passwords, and prefer end-to-end encryption. Do not expose dsh to a relay whose access policy you do not control.
Requirements

What you need

🖥

A server

With a public IP. The relay is a single Node process using roughly 30 MB of RAM — hardware requirements are minimal.

🌐

A domain (the apex)

A domain you can add DNS records to, e.g. tunnel.example.com. Two A records point at the relay's IP: the apex itself and the *.apex wildcard.

🔐

TLS for *.apex

Three options below. Wildcard certificates cover one label deep, so tunnel names stay flat (e.g. alice.tunnel.example.com) — the relay enforces this as well.

A  tunnel.example.com    → <relay IP>   # the apex: agents dial it; also the login host
A  *.tunnel.example.com  → <relay IP>   # the wildcard: every tunnel lives here
Deployment

Three steps

Run the relay

Option A — npm (Node ≥ 20)

DSHN_APEX=tunnel.example.com \
DSHN_RELAY_PORT=8787 \
DSHN_COOKIE_SECRET=$(openssl rand -hex 32) \
DSHN_CLAIMS=/var/lib/dshn/claims.json \
  npx @dshn/relay

For long-term operation, register it as a systemd service (DynamicUser + StateDirectory, starts with the system):

# /etc/systemd/system/dshn-relay.service
[Unit]
Description=dshn relay
After=network.target

[Service]
Environment=DSHN_APEX=tunnel.example.com
Environment=DSHN_RELAY_PORT=8787
Environment=DSHN_COOKIE_SECRET=<output of openssl rand -hex 32>
Environment=DSHN_CLAIMS=/var/lib/dshn/claims.json
ExecStart=/usr/bin/npx --yes @dshn/relay
Restart=always
DynamicUser=yes
StateDirectory=dshn

[Install]
WantedBy=multi-user.target
sudo systemctl enable --now dshn-relay

Option B — Docker

docker run -d --name dshn-relay --restart unless-stopped \
  -p 8787:8787 \
  -e DSHN_APEX=tunnel.example.com \
  -e DSHN_COOKIE_SECRET=$(openssl rand -hex 32) \
  -e DSHN_CLAIMS=/data/claims.json \
  -v dshn-data:/data \
  ghcr.io/jsdvjx/dshn-relay:latest

The repository also provides a docker-compose.yml (docker compose up -d).

Configure TLS (pick one)

The relay carries WebSockets, which require wss:// (TLS) end-to-end.

Behind Cloudflare (simplest; hides your origin). Proxy *.apex and the apex (orange cloud) to the relay. The relay serves plain HTTP and Cloudflare terminates TLS; set SSL mode to Full. Cloudflare closes idle WebSockets after roughly 100 seconds; the relay heartbeats every 25, so tunnels are unaffected. Harden the origin to accept only Cloudflare's IP ranges and enable Authenticated Origin Pulls — the origin trusts cf-connecting-ip.

Standalone with a real certificate (no Cloudflare). Obtain a wildcard certificate for *.apex via Let's Encrypt DNS-01 (certbot --preferred-challenges dns) and serve 443 directly: 

DSHN_APEX=tunnel.example.com DSHN_RELAY_PORT=443 \
DSHN_COOKIE_SECRET=… DSHN_CLAIMS=/var/lib/dshn/claims.json \
DSHN_TLS_CERT=/etc/letsencrypt/live/tunnel.example.com/fullchain.pem \
DSHN_TLS_KEY=/etc/letsencrypt/live/tunnel.example.com/privkey.pem \
  npx @dshn/relay

Binding 443 requires root or CAP_NET_BIND_SERVICE; agents rely on the public CA and need no extra configuration.

Self-signed (private / internal). Serve HTTPS with a self-signed certificate whose SAN covers *.apex, and pin it on the agent side with DSHN_ORIGIN_CA (next step).

Point your dsh agents at your relay

Install the plugin as usual, and set the relay host in the environment when launching dsh:

dsh plugin --profile web add @dshn/agent
DSHN_RELAY_HOST=wss://tunnel.example.com dsh --profile web

DSHN_RELAY_HOST takes any host that reaches your relay: the apex works, as does the reserved relay.<apex> subdomain (users cannot claim it); include the port when it is not 443 (wss://tunnel.example.com:8787). For a self-signed relay, also set DSHN_ORIGIN_CA to the relay's certificate PEM, which the agent pins as its sole CA.

Then open dsh → Settings → Public forwarding, enter a subdomain prefix and a password, and connect. The first agent to claim a free subdomain sets its password (trust-on-first-use), stored as a scrypt hash on your relay.

Reference

Relay environment variables

VariableRequiredDefaultPurpose
DSHN_COOKIE_SECRET✅—HMAC secret for login-session cookies (rotating it logs everyone out)
DSHN_APEX—ds.hnthe apex domain the wildcard hangs off
DSHN_RELAY_PORT—8787listen port
DSHN_CLAIMS—./claims.jsonJSON file the relay creates and maintains: subdomain → scrypt hash
DSHN_TLS_CERT / DSHN_TLS_KEY——PEM paths to serve HTTPS directly (omit to serve plain HTTP behind a TLS-terminating proxy)
DSHN_SITE——optional landing-page index.html for the bare apex (flat sibling .html/.css assets served too)
DSHN_DEBUG——set to log connection lifecycle to stderr
✅

Fails closed. The relay refuses to start without DSHN_COOKIE_SECRET — misconfiguration results in a failed start, never an unauthenticated relay.

💾

Back up claims.json. It is the only record of subdomain ownership; losing it frees every name for re-claiming. It is written atomically with mode 600.

1️⃣

One agent per subdomain. Exactly one live agent may hold a subdomain at a time; a second agent with the same credential replaces the first. Run one agent per (subdomain, password).
